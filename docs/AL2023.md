# hb on Amazon Linux 2023

hb started on Fedora. This page says what differs on Amazon Linux 2023 (AL2023) and
what hb does about each difference. The facts were checked against AWS's AL2023 user
guide and release notes (release 2023.12, November 2026). The test bed is the official
container image (`tests/al2023.sh`); the first real box comes after that.

## What differs, and what hb does

| Topic | On AL2023 | In hb |
|---|---|---|
| Python | `/usr/bin/python3` is 3.9 for AL2023's whole life, and AWS says not to repoint it. 3.11, 3.12, 3.13 and 3.14 install beside it as `/usr/bin/python3.N` | hb needs 3.11 or newer (`tomllib`). Every Python tool first imports `hbkit.start`, which re-runs it on the newest `/usr/bin/python3.N` from 3.11 up, with the same `-I -B` flags, arguments and environment. Install one: `sudo dnf install python3.13` (supported until mid-2029, like AL2023) |
| Kernel packages | `kernel` (6.1), `kernel6.12`, `kernel6.18`, side by side; there is no `kernel-core`. Installing another line doesn't make it the default: that is a separate `grubby --set-default` | a kernel only counts as a reason to reboot when it's the one the next boot starts (`grubby --default-kernel`), never just the newest installed, or `hb upgrade` would reboot into the same kernel night after night. When grubby can't say (it needs root), that's "can't tell", a warning. The digest recognises all of them (`util.KERNEL_RPM`). `dnf needs-restarting -r` comes from `dnf-utils`, installed on the standard AMI |
| dnf | dnf 4 (Fedora has dnf 5) | `hb rebuild` installs with `--setopt=strict=False`, which both understand; dnf 4 has no `--skip-unavailable`. `repoquery` output is read the same way on both |
| Updates | deterministic: the box stays on the release it has, so a plain `dnf upgrade` doesn't move it to a newer one. `--releasever=latest` (or a version) does, once; `dnf check-release-update` says what is newer | `upgrade.release = "latest"` resolves the newest release each night and passes it as `--releasever`, never moving to another major version; or pin one release. With `security_only`, `repos = ["amazonlinux"]`, `reboot = "never"` and `after` rules (test, then restart what changed; a failed test stays pending and blocks reboots until it works) it does what a careful nightly security job does. The transaction has no deadline (the check warns after 3 hours). `hb upgrade status` prints the exact command |
| Root filesystem | XFS | no `hb snapshot` (btrfs only). `hb backup` reads the live files, and its coverage report says so |
| SELinux | permissive | hb has only been run with SELinux disabled or permissive |
| Firewall | firewalld, nftables and iptables are in the repositories but not on the AMI | `hb fw` needs firewalld. On a Kubernetes node, and with security groups in front, think twice before adding it |
| SSH | EC2 Instance Connect's package adds `AuthorizedKeysCommand` to `/etc/ssh/sshd_config` itself. `sshd_config.d/` is read first and the first value wins | `hb ssh` pins `AuthorizedKeysCommand none` in its drop-in, so it would turn Instance Connect off. Don't apply `hb ssh` where Instance Connect is used |
| restic | not packaged (EPEL isn't supported; SPAL has no restic) | `hb backup` needs a restic binary from elsewhere |
| cron, syslog | cronie and rsyslog aren't installed by default; the journal persists | hb uses systemd timers and the journal only |
| Instance metadata | IMDSv2 required, hop limit 2, so pods can usually reach the instance role | `phase0/inventory.sh` reports the role |
| Default user | `ec2-user`, passwordless sudo through cloud-init | `hb harden` audits NOPASSWD when asked |

## Trying it on a box without changing anything

With no keys in `hb.toml`, every tool manages nothing. `hb install` then places the
code and the units without enabling a timer, and every `status`, `plan` and `check`
only reads.

    sudo dnf install python3.13             # if no python3.11+ is there yet
    git clone https://github.com/<you>/hardening-base && cd hardening-base
    printf '[install]\ntimers = []\n' > hb.toml
    sudo ./hb install plan                  # code, link, config, units; no timers
    sudo ./hb install apply
    sudo hb check
    sudo hb health status; sudo hb k8s status; sudo hb harden status   # and so on

Adopt tools one at a time after that, read-only ones first.

## Testing

    tests/al2023.sh

It builds a small image from `amazonlinux:2023` (plus python3.13, dnf-utils, git, make),
copies in only git's files, runs `hb check` as root with no `hb.toml`, then the test
suite as a normal user under python3.13. Systemd, sshd, PAM and the kernel aren't in a
container, so those parts are tested on the box itself.
